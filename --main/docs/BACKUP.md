# Резервное копирование, восстановление и хранение

## Создать и проверить копию

Из папки проекта (Linux или Windows PowerShell, Node.js 24 и Docker Desktop):

```powershell
npm run backup -- backups/my-copy
npm run restore:check -- backups/my-copy
```

Для согласованной копии скрипт кратковременно останавливает приложение, выгружает PostgreSQL в custom format, архивирует приватный volume файлов, создает SHA-256 каждого файла и архивов, записывает счетчики таблиц. В finally он запускает ранее работавшее приложение. Существующую папку копии не перезаписывает. База остается запущенной; одновременные ручные записи SQL во время копии не допускаются.

Секреты .env в копию не входят. Сохраните конфигурацию отдельно защищенным способом. Содержимое database.dump и files.tar.gz — приватные данные, а не безопасный публичный артефакт. Папка backups исключена из Git и Docker context. Скрипт не выполняет шифрование: перед выносом копии используйте согласованное шифрованное хранилище с ключом отдельно от сервера.

Проверка восстановления сверяет SHA-256 архивов, создает **отдельную временную** PostgreSQL базу и временный volume, выполняет pg_restore, сравнивает счетчики таблиц с manifest, извлекает файлы, проверяет все файловые SHA-256 и наличие файлов по ссылкам БД. В finally удаляет только созданные для проверки временные ресурсы. Рабочую базу и volume не заменяет. Это проверено на фактической копии с учетными записями, документами, версиями и вложениями.

## Восстановить после инцидента

1. Приостановить запись, сохранить текущую поврежденную среду отдельно; не выполнять безусловное удаление working volumes.
2. На отдельной изолированной машине/новых volumes проверить архивы через `restore:check` и согласовать выбранную точку восстановления.
3. Восстановить custom dump в новую пустую PostgreSQL базу командой pg_restore с no-owner, архив файлов — в новый приватный volume. Права файлов — только пользователь контейнера node, каталог 0700, файлы 0600.
4. Подключить отдельный экземпляр приложения к восстановленной базе и файлам, используя защищенно восстановленные настройки и SMTP. Сессии из старого dump аннулировать SQL-операцией `DELETE FROM sessions` после согласования инцидента; пользователей попросить войти заново. При компрометации заменить секреты и отозвать reset/invitation tokens.
5. Проверить вход, роли двух домов, документы, версии, обращения и скачивание; только после этого переключить трафик. Реальный аварийный перенос на внешнюю машину в Казахстане не выполнялся.

Расписание, off-site копирование, шифрование, мониторинг успешности и периодический restore drill организует оператор. Не храните единственную копию рядом с той же базой/диском.

## Выгрузка и удаление

Председатель может скачать защищенный ZIP данных своего дома через настройки. Он содержит сведения дома, доступные исходные записи, историю версий и файлы; это приватная выгрузка, не публикация жителям. Для больших объемов свыше 100 МБ используется операторский backup.

В интерфейсе архивирование меняет доступ, но не уничтожает оригинал или историю. Универсальной кнопки «удалить все документы» нет: сроки хранения могут зависеть от вида материала и правового основания. При запросе удаления оператор проверяет заявителя, вид данных, применимые сроки/обязательства и возможное ограничение обработки, фиксирует решение, отзывает ненужное членство/приглашения, согласует точечное удаление или хранение. Копии и backup также входят в политику сроков. Конкретные обязательные сроки автоматически не определяются и не выдумываются.
