# Запуск и ограниченный пилот

## На Windows

Перед запуском можно выполнить `npm.cmd run pilot:check`: проверяются Node.js,
Docker Compose и доступность Linux Engine без изменения данных и конфигурации.
План развития и критерии приемки первого дома: [ROADMAP.md](ROADMAP.md).

1. Установите Docker Desktop, включите Linux containers и WSL2. Дождитесь запуска Docker.
2. Установите Node.js 24 LTS. Распакуйте проект, откройте папку с package.json в PowerShell.
3. Выполните `npm run pilot` (либо `npm.cmd run pilot`, если PowerShell блокирует npm.ps1).
4. На своем ноутбуке откройте `http://localhost:3000/?mode=work`. Создайте учетную запись, дом и приглашение. Это локальный сервер, не адрес опубликованного сайта.
5. Для двух независимых сессий используйте обычное и приватное окно браузера. Восстановление пароля проверяйте в локальной почте `http://localhost:8025`. Реальное письмо наружу локальный Mailpit не отправляет.

Идемпотентный повторный запуск сохраняет named volumes. `.env` создается только при отсутствии, с новым случайным паролем PostgreSQL; его не пересылают в чат и не добавляют в Git. При переносе среды сохраняйте этот файл отдельно безопасным способом. Если порт занят, укажите свободный HOST_PORT и соответствующий PUBLIC_ORIGIN.

Остановить: `npm run pilot:stop`. Смотреть безопасные журналы приложения: `npm run pilot:logs`. Удаление volumes — отдельная операция оператора после резервной копии, не обычная остановка.

## Размещение в Казахстане — требуется оператор

Подготовлены `compose.production.yaml` и `ops/Caddyfile`. Публикация и создание внешних аккаунтов в ходе этой задачи не выполнялись.

1. Выберите инфраструктуру физически в Казахстане и проверьте условия обработки/хранения данных, доступ администраторов и резервное хранилище. Обычные Docker volumes располагаются там, где выбран сервер; географию проект самостоятельно не подтверждает.
2. Установите Docker Compose v2 с поддержкой `!reset` (не ниже 2.24.4). Разместите приватный .env с отдельными новыми секретами. Не переносите тестовую базу в настоящий пилот. База и файлы должны размещаться на защищенном диске, резервные копии — шифроваться и храниться отдельно.
3. Настройте DOMAIN, DNS A/AAAA, доступ к 80/443. Укажите PUBLIC_ORIGIN=https://ваш-домен и ALLOW_INSECURE_LOCAL=false. Caddy терминирует HTTPS и проксирует один origin на API; cookie становятся Secure. Самостоятельный выпуск реального сертификата и DNS не проверялись.
4. Укажите настоящий SMTP_HOST/PORT/SECURE/USER/PASSWORD/FROM. Mailpit в production-профиль не входит. Для STARTTLS используется TLS, проверка сертификатов не отключается. Проверьте доставку, SPF/DKIM/DMARC и полный reset-сценарий на выбранном SMTP. Без настройки доставка настоящих писем не подтверждается.
5. Выполните `docker compose -f compose.yaml -f compose.production.yaml up --build -d --wait`. В production overlay наружу открывается только Caddy; база/файлы и порт Node напрямую не публикуются. TRUST_PROXY ограничен подсетью прокси. Не открывайте Mailpit в интернет.
6. Проверьте health, создание дома, приглашение, вход с разных устройств, файлы, восстановление и backup/restore до использования реальных данных. Текущие браузерные проверки выполнялись в Chromium, а не на физических Android/iPhone.

ИИ необязателен. Если включаете: выберите провайдера и действующую модель, проверьте договор/основания передачи и размещение, добавьте серверный AI_API_KEY, AI_BASE_URL, AI_MODEL, AI_ENABLED=true и месячный AI_MONTHLY_REQUEST_LIMIT. Затем председатель отдельно разрешает передачу дому. Нет секретов в VITE_* или frontend. Контакты маскируются, ФИО в свободном тексте могут сохраниться. Реальный API-вызов и выставляемый счет провайдера пока не проверены; ограничивается число запросов, не фактический денежный счет.

## Ручное подключение дома

Регистрация и создание дома не подтверждают полномочия. Статус — pending_review. Перед настоящим пилотом оператор отдельно проверяет представителя, основание управления и контакт для связи по согласованной процедуре; удостоверения, ИИН и подписи обычное приложение не собирает.

После документированной проверки оператор выполняет:

```bash
docker compose exec -T app node ops/admin.mjs approve-house UUID_ДОМА
```

Для приостановки: `suspend-house UUID_ДОМА`. Для отзыва членства жителя: `revoke-member UUID_ЧЛЕНСТВА`. Действия аудируются; передача председательства не выполняется произвольным нажатием жителя. Статус не объявляется государственной верификацией.

## Проверки разработчика

Функциональные тесты — `npm test`. Интеграционные — `DATABASE_URL=.../uykomek_test npm run test:server`. Скрипт намеренно отказывается работать с БД, имя которой не заканчивается на `_test`. Создайте ее отдельно. Для reset-тестов нужен локальный Mailpit на 127.0.0.1:51025/58025; это отдельные тестовые порты. Настоящая внешняя модель заменена адаптером внутри теста, без ключа и без платного вызова.

`node scripts/check-pilot.mjs` создает вымышленные учетные записи/дом через UI и проверяет две сессии. `check-pilot-wizard.mjs` проверяет мастер с задержкой ответа, выгрузку и конфликт. Скрипты ограничены localhost и запускаются отдельной командой; не направляйте их на реальную рабочую базу. Старт Docker никаких тестовых учетных записей сам не создает. Для быстрой демонстрации без сервера сохранен прежний режим `/`.

Для разработки UI: `npm ci`, `npm run dev`. Для сервера: задайте DATABASE_URL и PUBLIC_ORIGIN в окружении, затем `npm run dev:server`. Сам сервер отдает готовый `dist`, поэтому после `npm run build` можно использовать один адрес без Vite proxy.

В облачной машине для Docker build требовался доверенный пакет CA из платформы, переданный временным BuildKit secret `trusted_ca`. Отключение TLS/проверки пакетов не использовалось. Обычная сборка без корпоративного прокси использует стандартный CA образа. Секрет сборки не копируется в образ.

## Пределы MVP перед настоящим пилотом

- Не заявляются полное соответствие законодательству, подтверждение собственности, полномочий, законности собрания или расходов. Даты/версии проверенных форм сохранены из предыдущего этапа.
- Нет OCR, ЭЦП, платежей, общей актуальной правовой базы, антивирусного сервиса и автоматического удаления по срокам. Загрузка разрешенных типов не означает юридическую или антивирусную экспертизу документа.
- Нужны политика обработки/хранения, основания доступа и согласий, проверка инфраструктуры, SMTP/HTTPS, процедуры инцидентов и приемочные испытания на реальных устройствах.
- Отправка обращений, запись и серверный выход требуют связи с API. Офлайн ошибка не выдается за успех; отложенной отправки и сложной синхронизации нет.
- Polling и версии защищают от незаметной перезаписи; файловая и SQL-транзакции не образуют распределенную транзакцию. После аварийной ошибки возможен неподвязанный файл; оператор проверяет ссылки и не удаляет материалы автоматически.
- GitHub Pages не обслуживает PostgreSQL/API. Подготовленный Docker-проект требует отдельного размещения; на момент проверки публичного рабочего сайта нет.
